# 低功耗 NAS：性能与 Emby 功能审查

日期：2026-11-10  
代码基线：`af2706e`  
目标：NAS 提供媒体目录、Emby 兼容接口、直链解析和观看记录，视频优先由客户端直连源站播放。

## 结论

**302 直链播放的方向适合低功耗 NAS；当前主要问题在资源同步正确性和大库后台处理，而非视频转码。建议先修复同步闭环和整库开销，再扩大媒体库。**

当前实现已经以 `strm.txt` 为资源导入、追更的权威清单，业务库为 PostgreSQL。`EnsureSQLiteReader` 已成为空操作，不能继续用 README 中“SQLite 增量监控”的描述判断当前行为。保留现有 PostgreSQL 和客户端直播放架构，优先消除不必要的全量操作，比更换数据库更直接。

## 优先修复的问题

### 1. P1：完整对账不再识别源端删除

- 位置：`internal/integration/pipeline.go:485–527,577–578`；`internal/resource/discovery/service.go:711–725`。
- `SyncRootsFromManifest` 仅将当前存在条目送入 `ManualSnapshot.Nodes`，没有生成 `Missing`。`RunFullSyncRoot` 与增量任务最终走同一条路径。清单里一个条目消失，旧资源不会进入 `MISSING`；整目录清空则直接记成功。
- **复现：导入 A、B，清单删除 A，再执行完整对账，A 仍为 `ACTIVE`。**
- 影响：后台可用性失真，源端移动/改名后旧条目残留，客户端继续看到失效资源。
- 修复：完整成功读取清单后，按监控根进行集合差异对账；缺失资源按 `keep` 策略保留文件和观看记录，只更新可用性。读取失败和不完整清单不能推进基线。

### 2. P1：同步失败被吞掉，变化指纹却提前推进

- 位置：`internal/integration/pipeline.go:517–527,570–574`；`internal/scheduler/scheduler.go:283–318`。
- 单根 `ApplyManualSnapshot` 失败只记录日志，循环结束返回 `nil`；`RunFullSyncRoot` 找不到批次时还会返回 `SUCCESS`。调度器在真正同步前已经更新 `lastManifestFP`。
- **复现：关闭隔离业务库后执行清单同步，日志记录 `sql: database is closed`，调用仍返回 `nil`。**
- 影响：任务看似成功，实际资源未入库；清单不再变化时，指纹门控阻止同一变化正常重试，只能依赖其他路径重新触发。
- 修复：汇总并返回每根错误，持久化失败状态；仅在成功完成对账后推进对应检查点。启动时应对账停机期间的变化，而非仅记下当前指纹后返回。

### 3. P1：局部更新仍有整库快照和整库数据库写入成本

- 位置：`internal/embyserver/scanner.go:121–126,186–192,417`；`internal/embyserver/snapshot.go:17–32,63–140`。
- 每次局部扫描先反序列化整库 `scan_snapshots.data`，把未涉及路径复制到 `current`，随后将所有媒体路径 COPY 到临时表，再序列化并重写整份快照。`commitSnapshot` 的“当前存在条目可用性 UPDATE”也覆盖整个媒体库。
- **合成实验：40 万条路径，快照 JSON 34.0 MiB；构造、编码和解码后堆内存增量约 207.3 MiB，累计分配约 330.5 MiB。**这测量的是快照数据结构，不包含 PostgreSQL、FFprobe、HTTP 请求与完整服务 RSS。
- 影响：更新一集的资源成本仍随整库规模增长；不同库扫描并发会叠加内存、WAL 和磁盘压力。当前扫描、更新各自默认并发 2，不能视为总并发只有 2。
- 修复：将快照按路径分行保存，局部任务只更新本次范围；完整对账使用分批暂存表和扫描代次。低功耗配置先将扫描与更新并发各设为 1，再建立共享后台资源预算。

### 4. P1：清单“流式读取”之后又积累全量对象，并使用大事务逐条写库

- 位置：`internal/integration/pipeline.go:476–517`；`internal/resource/discovery/service.go:609–638,641–741`。
- `StreamMultiPrefix` 回调将所有匹配项放进 `matchedEntries`，随后再构造整根 `ManualNode` 切片；`commitManual` 在一个事务里逐项查询、更新，完成后 `ApplyManualSnapshot` 又按每个 ID 查询并构造完整返回切片，而清单调用者丢弃该返回值。
- 影响：大范围导入和追更会同时持有多份条目对象、产生大量数据库往返和长事务；清单变化后的处理量取决于匹配根总量，而非实际变更量。
- 修复：流式分批写暂存表，数据库内批量差异计算；控制每批事务长度，提供不构造完整结果切片的批处理入口。

### 5. P2：空闲监控会退化为每秒执行任务并写状态

- 位置：`internal/scheduler/scheduler.go:171–199,224–260,283–299`。
- 根达到扫描时间后，定时器每秒调用任务。清单没变化时直接返回，不更新根的 `LastScannedAt`，于是下一秒该根仍“到期”；每次任务仍执行开始和结束两次状态写入。
- 影响：静态库也持续产生数据库事务和磁盘活动，与低功耗 NAS 的空闲、休眠目标冲突。空根分支还把 `now` 传到了 `sourceNodeID` 参数，而没有更新扫描时间（`pipeline.go:489`）。
- 修复：区分“已检查”和“有变化并同步”，无变化也安排下一检查时间；在指纹变化或实际执行时才记录任务运行状态，并修正空根参数。

### 6. P2：平铺剧集直接入库会将 Series 覆盖为 Season

- 位置：`internal/embyserver/direct_publish.go:140–145,181–200`。
- 平铺分集没有 `Season` 目录时，`seriesDir` 与 `seasonDir` 相同，二者产生同一个 ID、同一个唯一 `path`；Season 的 upsert 随后覆盖 Series，并形成自引用 parent。
- **真实 PostgreSQL 复现：分别发布一个标准目录剧集与一个平铺剧集，两个调用均成功，但 Series 总数仍为 1，平铺剧集的 Series 消失。**
- 修复：为平铺集使用独立逻辑季路径/ID；补充 PostgreSQL 下的平铺、特别篇、多季测试。另有路径未命中媒体库时使用不存在的 `libraries.type` 列（实际列为 `kind`）并忽略错误，可能回退进错误媒体库。

## 配置及部署核对

- `MEDIA_INFO_ROOT` 默认 `/app/data`，Compose 持久化的是 `/data`，未设置该变量。媒体信息 JSON 会写入容器可写层；数据库缓存仍在，但容器重建会丢失这份磁盘副本并在启动迁移时重新写入。统一使用 `/data` 下的持久化目录。
- 对低功耗默认档，建议扫描并发 1、更新并发 1、探测并发 1，关闭默认的下一集预探测，按实际需要开启浏览探测。更改默认值应保留现有用户显式配置。
- PostgreSQL 连接池已有最大 6、空闲 2 的限制。Compose 未配置服务 CPU/内存上限，内置 PostgreSQL 也没有专门低内存配置。应按 NAS 实际总内存设置服务预算，避免给 Go 单进程设上限后遗漏同容器 PostgreSQL 和 FFprobe。
- README 与部分文档仍描述 SQLite 权威扫描；当前清单解析器、热目录 SQLite 任务、旧文档并存。应以当前主链路统一功能说明和验收用例。

## 验证记录

- 默认 `go test ./...` 通过。
- 隔离 PostgreSQL 16 容器：限制为 1 CPU、768 MiB；Go 测试运行在本机。`TEST_DATABASE_URL=... go test -json ./...`：210 个顶层测试通过，2 个跳过；包含子测试共 290 项通过。跳过项为 40 万条目测试与真实小雅播放，40 万条目另行执行见下。
- 新增审查复现通过 Go overlay 加载，不修改产品源码：清单缺失检测、同步失败传播、平铺 Series 保留的预期断言均失败，结果支持上述问题。
- 快照实验使用合成路径和真实 `fileSnapshot` 类型；数据不是 NAS 实机内存测量。
- **40 万条目测试在 4 分钟上限处超时，停在构造目录数据的 INSERT 阶段**（`pagination_test.go:77`），尚未运行 EXPLAIN、深分页或真实列表接口计时。数据库镜像与容器运行环境均为 ARM64；这项结果说明该受限环境下批量建库开销显著，浏览延迟仍没有实测结论。
- 现有规模测试主要覆盖不合并版本的游标查询；真实普通用户列表默认还会进入 `mergeWhere` 的 `DISTINCT ON` 去重（`versions.go:19–34`、`main.go:1531–1533`）。后续应同时测默认合并、总数统计、StartIndex 随机跳页和连续游标分页，避免仅以索引查询时间作为客户端浏览时间。
- 本次没有部署到 NAS；真实小雅直链、客户端持续播放、停机恢复与 NAS 整机空闲功耗需在目标机器验收。临时测试容器及其数据已清理。

## 推荐实施顺序

1. 修复清单缺失对账、错误传播、成功检查点和空闲调度，先保证追更准确且空闲不持续写库。
2. 将局部快照更新和清单导入改成有界批处理，修正平铺分集发布及错误媒体库回退。
3. 统一持久化路径、低功耗默认设置与当前功能文档。
4. 在目标 NAS 按实际媒体规模验证：空闲 CPU/RSS/磁盘写入；导入与更新期间的峰值内存；首页、搜索、深分页及播放信息的 P50/P95；同时更新与播放时的响应；源端删除、恢复、同步失败和重启后的状态收敛。

完成标准是“实际客户端能顺畅浏览和持续播放，后台更新正确且资源有界”。当前已有的 302 播放和功能回归应保留，不建议为了降低表面内存而牺牲观看记录、缺失保护或错误可见性。
