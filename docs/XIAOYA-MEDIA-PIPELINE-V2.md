# 小雅资源识别、标准化刮削与 Emby 展示方案

状态：实施中（基础链路已落地）。日期：2026-11-08。

## 1. 目标与部署结论

将小雅 SQLite 中的来源目录转换为可播放、可追更的电影和节目媒体库，同时生成标准 STRM、NFO 和图片，供本服务的 Emby 兼容接口与独立 Emby 服务使用。

默认部署继续采用 **一个 Go 服务＋现有 PostgreSQL**，小雅作为外部来源。任务队列、识别结果、缓存索引均使用现有数据库；文件和图片保存在本地磁盘。默认不引入 Redis、消息中间件、搜索集群、MoviePilot 常驻服务或视频分析服务。

开发阶段采用新模型，不实现旧数据迁移兼容。现有数据库和文件的实际清空属于单独的部署操作。

设计必须同时满足：

- AList API 仅供后台浏览与搜索；入库、追更及播放定位均以 SQLite 为依据。

- 电影与节目分别识别；电视剧、动漫、综艺共享节目层级，但采用不同编号规则。
- 输入 `折月亮/01.strm` 时可以确定或确认节目身份，建立第 1 季及正确分集，生成规范文件。
- 输出电影 NFO、海报、背景图及可获取的 Logo；节目输出剧集、季、集元数据和图片。
- 来源身份、媒体身份、播放版本、输出路径相互分离。
- 全量读取不变成全量重新刮削；扫描内存不随全部节点数线性增长。
- 展示与播放优先于后台任务；网络刮削和图片失败不阻塞已识别资源播放。

## 2. 当前实现与目标的区别

当前 SQLite 路径为：读取 SQLite → 生成来源结构的 STRM → 扫描本地目录猜测电影/季集 → 补充元数据 → Emby API。

已完成一项关键性能收敛：SQLite 扫描现在按分页批次提交资源并立即物化，服务进程不再累积完整节点数组或整棵资源 Map；目录遍历本身仍维护当前层目录队列，完整对账仍需 O(N) 源读取。

目标路径为：读取 SQLite → 批量对账 → 识别媒体身份和季集 → 获取元数据 → 生成标准文件 → 发布媒体索引 → Emby API。标准文件和媒体索引共享识别结果，受管输出不再交给扫描器重复猜测。

本轮已切换：后台追更任务不再调用 AList；管理员选择入库时由 SQLite 解析路径；播放入口不再调用 AList `/api/fs/get`；SQLite 平铺数字分集会物化为 Season 1、规范分集 STRM 和基础 NFO；全量扫描按分页批次提交，不再累积完整节点数组；确定性的电影/节目/季集身份已写入 V2 识别表并生成播放版本任务；TMDB 匹配成功后会补齐电影、节目、季、集 NFO 及可用海报/背景图，歧义项进入管理员确认队列。Emby 直接使用 V2 媒体台账仍按后续阶段推进。

对应现有入口：

- `internal/resource/xiaoya/reader.go`：只读节点读取。
- `internal/resource/alist/`：仅保留浏览、搜索所需能力；导入入口转接 SQLite，移除独立 AList 追更。
- `internal/resource/discovery/service.go`、`store.go`：扫描、台账与差异。
- `internal/integration/pipeline.go`：流程编排。
- `internal/metadata/tmdb/`：TMDB 请求与名称解析。
- `internal/strm/`：路径、STRM 与附件写入。
- `internal/embyserver/`：媒体索引、接口与播放解析。

## 3. 从 SQLite 到客户端的处理顺序

| 阶段 | 输入与工作 | 持久结果 | 失败后的行为 |
|---|---|---|---|
| 发现 | 只读读取监控范围内节点，分页传输 | 扫描批次与暂存清单 | 不判缺失，不推进未提交游标 |
| 对账 | 按来源身份比较新增、修改、移动、缺失 | 来源资源、变更任务 | 已提交批次可重试，业务更新与任务同时提交 |
| 识别 | 判定电影/节目、匹配作品、解析季集 | 识别结果与人工绑定 | 歧义进入待确认，网络错误进入重试 |
| 刮削 | 按作品及季获取元数据，复用缓存 | 媒体元数据与图片任务 | 有效旧元数据继续使用；编号明确的集保留基本标题 |
| 生成 | 生成 STRM、NFO，独立下载图片 | 产物清单与路径归属 | 重试同一目标，不覆盖其他资源 |
| 发布 | 核对必需产物及播放定位，提交父子关系 | 媒体库成员与可展示版本 | 原已发布版本保持可见，新版本暂不发布 |
| 展示 | Emby API 查询电影、剧集、季、集及图片 | 客户端海报墙和选集 | 返回准确状态，不把空剧集当作正常可播放作品 |
| 播放 | 使用由 SQLite 得到的播放定位，访问文件入口 | 播放会话与观看进度 | 定点重读节点后仍失败则反馈，不调用 AList API |

### SQLite 是唯一资源入库依据，AList 仅供后台浏览和搜索

AList 的资源 API 仅允许在用户主动浏览目录、搜索资源时调用 `/api/fs/list` 和 `/api/fs/search`。鉴权仅服务于这两项操作，不向后台任务或播放流程提供 AList API 客户端。自动发现、手动导入、追更、对账、附件定位和播放定位统一以小雅 SQLite 节点为依据。

| 用途 | 数据入口 | 处理规则 |
|---|---|---|
| 后台浏览目录、搜索资源 | AList `/api/fs/list`、`/api/fs/search` | 用户操作时分页请求，不在后台自动遍历 |
| 从浏览结果选择单文件或目录入库 | SQLite | 只接收所选来源连接和原始路径，重新解析 SQLite 节点及子树 |
| 自动发现、目录追更、全量对账 | SQLite | 使用统一监控范围、游标和快照机制 |
| 来源附件定位 | SQLite 的路径及 content | 下载文件本体使用对应 HTTP 文件入口，不调用 AList 文件详情 API |
| 播放定位与更新 | SQLite 的路径及 content，以及其本地已同步记录 | 正常播放使用本地记录；入口失效时可定点重读 SQLite 节点 |
| 影视元数据、海报 | 本地有效 NFO、TMDB 等元数据服务 | 正常刮削 HTTP 请求保留，与 AList 资源 API 分开 |

选择入库时，对 AList 返回路径按明确的连接路径映射定位 SQLite，不能把搜索结果本身作为已入库资源。找不到对应节点时显示“该路径尚未进入小雅 SQLite，暂不能入库”；等待小雅数据库更新后重试，不改用 `/api/fs/get` 或递归 `/api/fs/list` 补齐。单次导入与持续追更使用同一个 SQLite 入口，只区别是否注册后续监控。资源按 SQLite 来源键去重，不再保留独立 AList 导入台账和 AList 追更任务。

SQLite 保存的是目录和播放/附件定位信息，不保存视频和图片本体。根据其中地址访问小雅 `/d/` 等文件入口、跟随 HTTP 重定向以及访问 TMDB 图片服务仍属于正常文件传输。我们的服务不在这些流程调用 AList `/api/fs/*`；小雅文件服务内部如何解析网盘由小雅负责。

播放失败时，可在本地定位失效后对同一节点做一次有界重读并复用短期结果；节点未变且入口仍不可用时明确返回失败，不调用 `/api/fs/get` 刷新签名或绕过重定向循环。SQLite 不可用时既有有效播放定位可继续使用，但新增入库和同步报错等待恢复。当前播放入口已采用无 AList 兜底路径；依赖该兜底才能播放的资源，必须验证小雅文件入口可用，不能宣称 SQLite 能生成新的网盘签名。

### 两种展示方式

**默认：SenPlayer 直接连接本服务。** 列表、图片、季集、播放信息均由本服务的 Emby 兼容接口返回；客户端不读取 SQLite/NFO。

**可选：独立 Emby 扫描输出目录。** 同一套产物供外部 Emby 使用。目录完成后合并发送媒体库刷新通知，禁止每个附件生成后触发一次全库扫描。外部 Emby 是可选消费者，不作为默认必需容器。

## 4. 新数据模型

以下是逻辑表职责，最终字段和 SQL 在实现阶段固化。

| 表/对象 | 关键字段与约束 |
|---|---|
| `source_connections` | 来源配置、来源代次；数据库更换后节点 ID 不能直接沿用旧身份 |
| `source_resources` | 独立 ID、来源连接/代次/节点 ID、父节点、原名、路径、内容、可用状态、业务修订号；来源键唯一 |
| `monitor_scopes` / `scope_resources` | 监控根、分类规则和资源成员；重叠范围不重复创建资源 |
| `scan_runs` / `scan_entries` | 批次、快照边界、范围、节点清单和内容；只有完整批次可用于缺失判定 |
| `recognition_results` | 来源修订号、规则版本、作品匹配、季集/分段信息、识别依据、状态及人工覆盖 |
| `media_items` | 独立 ID、类型 Movie/Series/Season/Episode、父级、季集号、标题、年份、元数据修订号 |
| `media_provider_ids` | provider、媒体类型、外部 ID；禁止混用 TMDB movie 与 tv 的数字 ID |
| `media_versions` / `version_resources` | 媒体条目、来源版本、质量标签、播放定位；组合文件与单文件分开描述 |
| `library_items` | 媒体库与条目的收录关系，同一媒体可进入多个库 |
| `media_artifacts` | 归属条目/版本、产物种类、目标路径、修订号、生成状态；目标路径唯一 |
| `work_jobs` | 去重键、阶段、输入修订号、状态、租约、重试时间、错误原因 |
| `metadata_cache` | provider、类型、ID、季号、语言、有效期和响应；不按本地文件重复缓存 |

核心约束：

1. Season 的 `(series_id, season_number)` 唯一，允许第 0 季；标准 Episode 的 `(season_id, episode_number)` 唯一。
2. 同一分集的不同来源/清晰度属于播放版本。综艺上中下是内容分段，不能伪装成可互换的播放版本。组合集或分段需要显式关联；首版未支持的形式进入待确认，不静默丢弃。
3. 观看记录关联媒体 ID；路径、标题、输出模板变化不改变身份。
4. 人工绑定优先，并限定作用范围；更新规则不得覆盖人工确认。
5. 源文件缺失只影响对应来源版本；其他版本可用时，媒体条目继续可播放。默认保留文件和观看记录，标记不可用，不自动删除产物。
6. 来源 URL 或认证内容不得出现在普通日志中；STRM 不写管理员 API Key。使用 SQLite 提供的播放定位及小雅路径型文件入口，不把短期 CDN 签名地址当作永久来源身份；禁止调用 AList 文件详情 API 兜底。

## 5. 资源同步：低内存且可核对完整性

建议索引：来源键唯一索引；来源父节点索引；范围成员 `(scope_id, resource_id)`；扫描清单 `(run_id, source_node_id)`；媒体父级与季集排序索引；媒体库成员索引；任务按可领取状态与 `run_after` 的索引。大规模查询用执行计划验证索引命中，不依靠每次查询临时全表递归。

### 5.1 日常增量

- 按来源连接维护读取游标，读取 `last_id < id <= snapshot_high_id`，同一来源的新节点只读一次，再分发到监控范围。
- 首次启用新监控范围必须建立自身基线，不能因为共享来源游标已推进而漏掉历史节点。
- 祖先路径解析使用有容量上限的缓存和本地目录索引；缓存不命中时批量读取，不为每个文件重复逐级查询。
- 比较当前批次对应旧记录，不加载整个资源库。来源变更、修订号更新、任务入队与页游标在一个短事务中提交。
- 快速新增通道依赖节点 ID 递增；旧节点修改、删除、低 ID 复用由全量对账覆盖。
- 最大 ID 回退、根节点身份变化或来源替换信号触发重新基线。最大 ID 未回退不能证明数据库未更换，因此保留周期全量对账和显式来源重置入口。

### 5.2 全量对账

1. 每个来源同时只允许一个扫描会话；受影响范围内全量与增量提交串行化，避免旧快照覆盖新事件。
2. 在一致 SQLite 读快照内分页读取。每批先落到 PostgreSQL 扫描暂存表，不在源读事务内调用 TMDB、下载图片或生成文件。
3. 范围遍历队列使用本地磁盘/数据库暂存，进程只保留当前批及有界缓存。若源库缺少有效 `parent_id` 索引，避免反复全表查询：改为一次按主键顺序导出节点，在本地暂存表建立父节点索引后筛选范围；不向小雅源库加索引。
4. 源快照完整读取并关闭后，按批次用暂存清单与历史台账集合比较；仅写入有变化的业务记录和任务。无变化资源无需每日重写内容及多个散列字段。
5. 暂存清单负责证明本轮出现过的节点，不更新每条业务记录的 `last_seen` 来代替清单。该清单仍有 O(N) 磁盘写入成本，需要计算配额。
6. 只有 `SOURCE_COMPLETE` 的清单可以判缺失；分批应用可在崩溃后继续，所有批次完成后标记 `APPLIED`。应用期间不并发提交更新的同范围扫描。
7. 缺失按各监控范围成员关系核对；退出一个范围不等于从其他重叠范围消失。未完成、取消、异常或磁盘空间不足的扫描不得执行缺失标记。
8. 后续识别/生成失败不回滚发现游标，由持久任务队列重试；不能要求“所有海报下载成功”才推进资源发现。

比较业务变化可采用字段比较或单一规范化指纹；不对视频内容计算散列，不每轮额外计算文件完整性校验。

### 5.3 源 SQLite 的 WAL 与一致性

SQLite WAL 的长读事务会限制 checkpoint 推进，可能导致源 WAL 增长；只读不等于对源系统零负载。[SQLite WAL 文档](https://www.sqlite.org/wal.html)

- 挂载源库所在本地目录及 WAL/SHM，维持只读访问；不将活动 WAL 数据库通过网络文件系统当本地库打开。
- 一致快照读取设置时限，默认起始值 120 秒；超时撤销未完成批次，不为了限时而把多次不一致分页拼成完整快照。
- 读取期间不因后台刮削队列拥堵而长时间暂停；暂存空间不足则结束扫描，避免长期占用源快照。
- 超时频繁时按非重叠监控范围拆分调度；单一范围仍过大时，可启用 SQLite 在线备份到本地快照文件的模式，验证所用驱动支持后使用。备份同样需要读取和磁盘空间，不能宣称零开销。
- 禁止直接复制正在使用的 `.db` 文件并忽略 WAL。备份/快照失败不降级成可能误删的缺失判断。

全量初始周期建议 24 小时，在用户设定的低峰窗口执行；增量默认 10 分钟。目录分批错峰；这是新增低功耗配置的建议值，现有 24 小时间隔并不自动代表夜间执行。

### 5.4 算法优化：变更门控、共享增量、热目录对账

首版优先实现以下优化，不增加常驻服务。

**1. 无变更门控。** 用独立、长期持有的只读连接，在事务外观察 `PRAGMA data_version`。同一连接上的值变化表示其他连接提交过修改；它不提供变化行清单，不能跨连接或重启直接比较。[SQLite data_version](https://www.sqlite.org/pragma.html#pragma_data_version)

门控仅在来源身份、监控配置不变且对应扫描通道无未完成检查时跳过源读取。分别维护“新增检查已覆盖”和“完整对账已覆盖”的状态：增量处理成功不能清除旧节点修改待对账标志。扫描前后版本变化时仍保留待检查状态；新连接、源文件替换、配置变更使门控失效，重新核对。已有队列任务、失败重试、元数据到期刷新不受该门控阻断。即使版本不变，也保留低频来源身份检查。

**2. 共享增量游标。** 同一来源的新 ID 区间只查询一次。监控根组成最小非重叠读取范围，子范围保留订阅及分类语义，由节点父关系分发变更。用 `id > cursor ORDER BY id LIMIT batch_size` 的键集分页，避免 OFFSET 随页数增加的跳过成本。首次启用子范围仍建立自己的基线。

**3. 热目录定点对账。** 最近新增过分集或用户显式追更的节目目录进入热队列；以节目子树为单位读取完整清单，覆盖旧 ID 的改名、链接变化和删除。目录增量不是仅数文件：必须比较节点 ID、父关系、名称和内容。

初始策略为全局新增检查每 10 分钟；热目录对账间隔从 30 分钟开始，连续无变化后按 30→60→120 分钟退避，上限 6 小时，有变化恢复到 30 分钟。具体值待 NAS 压测；最近变化和用户追更决定热度，TMDB“已完结”仅作为辅助线索。冷目录仍参与默认 24 小时全量对账。使用按 `next_due_at` 排序的持久任务索引选择到期范围，不在每轮把所有目录加载到内存排序。

定点对账有效性依赖源库父节点查询索引；索引缺失时不为每个热目录分别全表扫描，合并为一次来源级快照后本地筛选。当本轮热目录累计读取量接近全量成本时，合并请求，避免热扫描加全量造成重复负载。热目录扫描完成不更新其他范围的完整性状态。

**4. 批量集合差分。** 完整清单通过批量写入进入暂存表，以来源键连接历史记录，区分新增、删除和字段不同的行；按键分页应用差异，变化任务与台账一起提交。保留第 5.2 节的一致性条件，不将不同时间扫描的目录拼成一个可全局判缺失的快照。

**5. 按变化字段失效。** URL 变化只更新播放定位和 STRM；作品身份线索变化才重新识别；新增一集复用节目与季缓存；图片字段变化只更新图片任务。目录移动或改名时，按本地父关系索引使后代路径/匹配依赖失效，不能只更新目录一行而留下陈旧分集定位。

**6. 合并重复任务。** 同一节目短时间内连续增加多集时，合并一次作品/季元数据请求；单个资源只处理最新修订，中间修订任务标记 SUPERSEDED。合并窗口建议 5 秒且设置最长等待时间，避免持续更新导致永不执行。

### 5.5 暂不采用的捷径

- 源库目前使用的节点字段没有可靠修改时间或变更序号。没有源端维护的变更日志/摘要时，精确发现任意旧节点变化仍需检查相关节点；最大 ID、文件数、目录最大 ID 都不能证明内容未变。
- 首版不建立 Merkle 树：若摘要由我们计算，仍需读取所有子节点才能发现源变化；它不能省去源读取，还增加摘要维护与目录移动处理成本。
- 不使用 Bloom Filter 判定“没有变化”或直接删除：成员摘要无法表达文件内容修改，精确台账差分仍然需要执行。
- 不直接解析小雅 WAL 做 CDC，不给源库加触发器；保持只读、低维护成本。未来只有源端提供稳定的节点修订号或变更日志时，才评估真正的修改/删除增量。
- 不用 `.db` 文件 mtime 作为无变化判断，WAL 模式下主文件时间不足以反映提交。

## 6. 识别：电影和节目分开

### 6.1 作品匹配

依据优先级：人工绑定 → 有效外部 NFO → 路径 provider ID → 类型、剧名、年份搜索。搜索存在多个无法区分的候选时进入待确认，不直接取第一个。

电影与节目的 TMDB 查询分开。类别配置可作为识别线索，路径分类不能压过明确有效的媒体类型。保留“匹配依据”以便人工纠偏。

### 6.2 季集解析

- 优先使用有效分集 NFO，再解析 `SxxExx`、季目录、集名。
- 已确认节目下，平铺 `01`、`E01`、`第01集` 且没有明确季信息或冲突时，按配置的默认第 1 季规则处理，记录为推断。
- 明确第 0 季和第 2 季不能被默认值覆盖。
- 电影中的 `01` 不套用集号规则；上下部、片段与不同版本分别识别。
- 综艺日期、期号、上中下保留原始标记，对应元数据的分集顺序不能由目录遍历顺序替代。绝对编号动漫需明确编号映射，不按集数猜季。
- 只为实际存在的来源生成播放版本；TMDB 上存在但本地没有资源的分集不制造空 STRM。

### 6.3 请求复用与失效范围

同一节目只匹配一次，按季请求分集信息，不对每个 STRM 重复查询节目。并发请求使用 singleflight 合并；持久缓存键包含 provider、媒体类型、ID、季号及语言。

来源只改变播放定位时只更新版本和相关 STRM；身份线索改变才触发重识别。节目人工改绑或规则升级按依赖关系重新处理受影响季集。生成 NFO 是输出，不作为外部证据回灌覆盖识别结果。

媒体身份和季集已确定但在线元数据暂缺时，允许用有效本地字段生成基础 NFO 并发布；标题暂用来源标题或“第 N 集”，在线信息作为后续更新。身份尚不确定则保留在待确认队列。

TMDB 网络失败使用重试而非标记为匹配失败；尊重 429 和响应中的 Retry-After，重试采用退避与抖动。[TMDB 限流说明](https://developer.themoviedb.org/docs/rate-limiting)

## 7. 标准文件输出

年份策略默认 `auto`：有可靠年份追加，没有省略；支持 `omit`。目录默认不展示 TMDB 标签，冲突时加年份或媒体 ID。ID 始终写入 NFO。分类前缀可保留，例如“每日更新/电影/中国”，外部 Emby 应挂载实际影片目录的父层级。

### 电影样本

```text
每日更新/电影/中国/八仙！ (2026)/
  八仙！ (2026).strm
  movie.nfo
  八仙！ (2026).nfo
  八仙！ (2026)-poster.jpg
  八仙！ (2026)-fanart.jpg
  八仙！ (2026)-clearlogo.png
```

单版本的两个 NFO 来自同一份数据：`movie.nfo` 为作品信息，同名 NFO 同时可携带版本信息。多版本使用稳定版本后缀及各自同名 NFO，电影级 NFO 不写相互冲突的版本属性。

### 节目样本

```text
每日更新/电视剧/国产剧/折月亮 (2026)/
  tvshow.nfo
  poster.jpg
  fanart.jpg
  clearlogo.png
  Season 1/
    season.nfo
    poster.jpg
    折月亮 - S01E01 - 第 01 集.strm
    折月亮 - S01E01 - 第 01 集.nfo
    折月亮 - S01E01 - 第 01 集-thumb.jpg
```

有正式分集标题时使用正式标题。目录季号、文件名编号、NFO 编号和数据库编号必须一致。命名遵循 Emby 的剧集/季/分集结构建议。[Emby 命名文档](https://emby.media/support/articles/TV-Naming.html)

### 写入与恢复

- STRM 内容使用稳定来源定位/可用播放入口，不以输出文件名拼接上游地址。
- 文件写入采用同目录临时文件、原子替换；路径经过边界检查、字符处理和字节长度控制。
- 文件系统和数据库不是同一个事务：先记录目标修订与归属，生成必需文件，再用短事务发布该版本；崩溃后根据产物清单补齐，不能把半成品标记为完成。
- 首次发布要求 STRM 和必需 NFO 完成、播放定位存在；图片异步补充，不做首次播放前的逐集连通性探测。
- 元数据标题后补默认不反复移动已生成路径；显式“重新整理”才同步改名，并由同一条目任务锁协调附件和索引。
- 无图片时使用应用占位图，不把占位图写成伪造海报。低功耗模式只获取有限尺寸海报、背景图和分集图；Logo 有则下载，不下载无关图库。
- 图片磁盘缓存有容量上限；缓存淘汰仅删除可重建缓存，不删除媒体目录中的已发布附件。相同源图可复用下载，不引入额外对象存储。

## 8. Emby 索引与播放

- 受管资源由发布阶段直接更新索引，不再次遍历输出目录解析。外部非受管媒体保留独立扫描入口。
- 发布一个 Episode 时，在同一数据库事务中确保 Series、Season 和版本关联完整。
- 默认海报墙只显示至少有一个已发布播放版本的电影/节目；待确认和未完成任务在管理端展示，不产生只有海报的空壳。
- 已发布媒体的来源全部缺失时保留观看记录，标注不可用；不返回虚假的可用播放源。
- `Shows/{id}/Seasons`、`Shows/{id}/Episodes`、`SeasonId` 筛选使用直接父子关联和索引；DTO 返回 SeriesId、SeasonId、季集号及必要播放信息。
- 海报墙分页查询，批量补充图片/用户状态，避免逐条数据库查询和递归临时解析。浏览请求不能同步触发 TMDB 刮削。
- 热路径为媒体详情、图片缓存、播放定位与进度；使用本地已同步的 SQLite 定位，文件入口重定向结果可短期缓存，不调用 AList API；默认不运行视频转码或全库 ffprobe。

### 8.1 Web 展示界面与管理界面分离

Web 是同一服务下的两套工作界面：展示界面面向登录用户，管理界面仅管理员可进入。默认入口及登录成功后的默认落点均为展示界面；管理员也不默认跳转管理后台。

建议客户端路由使用 `/web/` 和 `/web/manage/`，避免与已有 `/admin/*` 管理 API 混用路径；实现时支持深链接、刷新及返回导航。

| 界面 | 主要内容 | 数据接口 |
|---|---|---|
| 展示首页 | 媒体库入口、电影/节目海报墙、搜索、排序、分页 | 当前用户的 Emby API |
| 电影详情 | 海报、背景图、简介、年份、演职员、播放版本、观看状态 | Emby 详情、图片和播放信息 API |
| 节目详情 | 节目介绍、季选择、分集缩略图、编号、标题、观看状态、版本 | Emby Seasons/Episodes/详情 API |
| 管理界面 | SQLite 监控、同步、任务、待确认识别、纠偏、重新刮削、标准文件整理、用户权限、配置与日志 | 受管理员鉴权的管理 API |

展示方向是播放器式浏览：以海报和背景图建立层级，节目详情显式显示季选择及分集列表；电脑和手机均能浏览。列表分页、图片懒加载并按显示尺寸请求，详情按需获取；不在首页预取每部剧的全部季集。管理界面则强调状态、失败原因和明确操作，不混入普通用户的海报墙。

管理员在展示详情页可见低干扰的“管理此影片/节目”入口，携带媒体 ID 跳转相应管理页；匹配纠偏、重新刮削、重命名整理等操作统一由管理界面执行。处理结束回到该详情页时，重新通过 Emby API 获取结果，不用管理接口的临时数据替代媒体详情。

### 8.2 权限必须由服务端执行

- 普通用户不显示管理入口，客户端路由守卫阻止加载管理页面；直接请求管理 API 时服务端返回 403。未认证请求返回 401。
- 登录后及恢复会话时获取服务端当前用户权限，不把 localStorage 中可修改的管理员标记当成授权依据。管理员角色撤销后，下一次管理请求立即拒绝，页面退出管理区。
- 所有管理接口逐项检查权限，包括任务、日志、配置以及挂在 Emby 路径下的刮削/刷新等管理动作。后台 AList 浏览与搜索也仅管理员可用。
- 展示界面使用当前用户登录令牌，不使用服务器管理员 API Key；服务端校验请求中的用户 ID、媒体库访问权和播放权限。个人观看状态更新属于用户自身操作，不属于管理员刮削权限。
- 管理模块按需加载；普通用户进入展示页不请求管理数据、不轮询管理任务。

### 8.3 展示界面作为 Emby 数据预览客户端

展示页面直接使用与播放器相同的 Emby 数据接口，不新增一套 Web 专用海报墙数据源。建议调用约定：

| 目的 | 接口 |
|---|---|
| 登录 | `POST /emby/Users/AuthenticateByName` |
| 媒体库 | `GET /emby/Users/{userId}/Views` |
| 海报墙/搜索 | `GET /emby/Items`，携带当前用户、媒体库、类型及分页参数 |
| 媒体详情 | `GET /emby/Users/{userId}/Items/{itemId}` |
| 季列表 | `GET /emby/Shows/{seriesId}/Seasons` |
| 分集列表 | `GET /emby/Shows/{seriesId}/Episodes`，按需携带 `SeasonId` |
| 图片 | `/emby/Items/{itemId}/Images/{imageType}` |
| 播放版本/播放信息 | `/emby/Items/{itemId}/PlaybackInfo`，遵循服务端支持的方法与当前用户权限 |

网页不能在缺季时自行合成“第 1 季”，也不能从管理台账补出接口未返回的分集；这样才能暴露 SenPlayer 同样会遇到的数据结构问题。无季、无集、图片加载失败、无播放源分别呈现准确状态，管理员可从详情进入管理页处理。

预览验收关注同账号、同媒体、同季集和版本数据一致。SenPlayer 的布局、缓存和具体请求参数仍通过实机验证；Web 预览不宣称像素级复刻。当前阶段要求播放器式展示及播放信息预览，浏览器内实际解码播放另行确定，不为此新增 NAS 转码服务。

## 9. 低配置 NAS 的执行预算

以下为待压测的低功耗档初始配置，不是已测性能或机器最低要求。

| 参数 | 初始值 | 调整依据 |
|---|---:|---|
| 同时全量扫描 | 全局 1 个 | 源库/WAL、磁盘与前台延迟 |
| 扫描批大小 | 最多 1,000 节点且最多约 4 MiB 有效载荷 | 行大小和进程内存；单行超限中止批次并报错，不据不完整清单判缺失 |
| 识别/元数据 worker | 1 个，外部请求全局最多并发 2 | 网络和限流 |
| TMDB 请求节流 | 初始最多 2 次/秒 | 尊重服务端限流，不当作官方额度 |
| 文件写入 worker | 1 个 | 小文件随机写负载 |
| 图片下载 worker | 1 个 | 网络、内存和图片解码峰值 |
| 前台数据库连接上限 | 4 | 实际并发与查询耗时 |
| 后台数据库连接上限 | 2 | 避免占满前台池；包括任务领取与暂存写入 |
| 内存缓存预算 | 约 32 MiB | 元数据、祖先索引合计；淘汰可重建项 |
| 图片缓存预算 | 初始 1 GiB | 可用磁盘与命中率 |
| Go 内存软目标 | 初始 256 MiB | 包含服务运行对象；不等于 RSS 硬上限 |

小内存机器必须同时为小雅、PostgreSQL、操作系统缓存预留空间，不以 Go 的软目标当作整个部署内存预算。PostgreSQL 保持低连接数，并限制后台查询的排序/哈希内存及并行度；`work_mem` 按查询操作分配，不能当成数据库总内存限制。

调度原则：

- 前台 API 使用独立连接预算，后台任务不能全部占用数据库连接。
- 全量错峰，默认串行；有播放会话或前台延迟持续升高时，暂停领取新的重任务，完成当前短操作。正在读取一致 SQLite 快照时按时限完成或取消，不能无限暂停。
- 不为每条节点启动 goroutine。进程内仅持有有界任务缓冲，积压保留在磁盘队列。
- 队列/暂存达到配置的磁盘配额时停止开始新扫描，已持久任务继续消化，管理端显示积压和空间需求。
- 任务暂存、历史日志按批次清理，保留最近完整扫描和恢复所需的未完成批次，不无限保存每轮完整目录副本。

## 10. 队列、组件与故障恢复

### 默认使用 PostgreSQL 持久队列

用短事务领取任务，`FOR UPDATE SKIP LOCKED` 允许 worker 避开已领取的行；事务提交后才执行网络/文件工作，不持有行锁等待下载。该机制适用于队列式访问，不用于要求完整一致结果的普通媒体查询。[PostgreSQL SELECT 文档](https://www.postgresql.org/docs/16/sql-select.html)

- 状态：PENDING、RUNNING、RETRY、DONE、FAILED、SUPERSEDED；人工识别歧义另外使用 NEEDS_REVIEW。
- 去重键包含阶段、对象、输入修订号和规则版本。任务至少执行一次，写入必须幂等。
- worker 领取后有租约和心跳；重启后到期任务可重新领取。
- 任务提交前校验输入修订号，旧任务不能覆盖新识别结果；同一产物归属的文件替换串行执行。
- 错误分类区分网络可重试、认证待配置、匹配待确认、磁盘空间不足；达到有限重试次数后进入失败列表，支持修复后重试。

### 其他组件的取舍

| 组件 | 默认决策 | 何时再引入 |
|---|---|---|
| Redis/RabbitMQ/Kafka | 不引入；现有数据库足以承载初期队列与状态 | 实测数据库队列成为瓶颈，且有多机调度需求 |
| Elasticsearch | 不引入；媒体查询使用 PostgreSQL 索引 | 搜索需求与压测证明现有索引不足 |
| MoviePilot/TMM 常驻 | 不作为运行依赖 | 用样本对照识别和输出，或用户已有独立部署 |
| 独立 Go worker | 首版同进程、有界 worker | NAS 资源不足且已有闲置主机，可远程承担元数据网络请求；文件提交仍由 NAS 执行 |
| 本地 SQLite 扫描快照 | 按需启用的磁盘文件，不增加常驻服务 | 源库扫描时间与 WAL 压力需要隔离 |

参考成熟工具的阶段划分和命名规则，复用本项目的 Go 实现。直接复制第三方源码前核对许可证；MoviePilot 标注 GPL-3.0。[MoviePilot](https://github.com/jxxghp/MoviePilot)、[TMM 重命名规则](https://www.tinymediamanager.org/docs/tvshows/renamer)。

## 11. 性能量级与测量方法

设监控节点数为 N，变化节点为 ΔN，独立节目/季数为 S，图片数为 A。无变更门控可跳过满足条件的源扫描；以下描述实际执行对账时的成本。

- 全量对账必然读取 O(N) 目录数据；暂存也需要 O(N) 磁盘空间。无可靠源变更日志时，不能仅凭最大 ID 排除旧节点修改。
- 合理索引下，按批次进行集合比较，业务写入接近 O(ΔN)，另有本轮清单写入；不宣称“无变化全量零写入”。
- 进程工作内存由批大小、缓存、worker 和查询返回限制决定，不能有 O(N) 节点数组、目录队列或历史 Map。
- 元数据请求按作品/季复用，数量主要随 S 和缓存失效变化，而非每集重复查剧名。
- 图片 I/O 随实际新增或更新的 A 增长；浏览图片缩放单独限并发并缓存结果。

压测数据集：1 万、10 万、100 万节点；覆盖宽目录、深目录、长路径、长 URL、大附件数量和重叠监控范围。每个规模测试首次基线、零变化全量、1% 变化全量、仅新增少量分集。

记录应用峰值 RSS/Go 堆、PostgreSQL 内存/CPU、扫描吞吐与总时长、SQL 次数、业务更新行数、WAL 增量、暂存大小、TMDB 请求次数、图片写入量，以及并发浏览/播放信息接口的 p50/p95。

验收目标：

- 同一预算下从 10 万增至 100 万节点，进程峰值内存不按节点数同比增长；核对数据库磁盘溢写，而不是将内存压力转移后忽略。
- 零变化全量不重写 STRM/NFO，不重新刮削全部媒体，不更新全部业务行。
- 同季首次处理时不按集数重复请求季元数据；缓存命中场景无多余外部请求。
- 记录后台开启前后前台 p95，建议以不超过空闲基线 1.5 倍为初始目标；实际硬件上的绝对延迟另行记录。
- 扫描耗时不预设“百万节点几分钟”；以实际 NAS、源库索引、存储介质和网络测量决定批量与调度参数。

## 12. 实施阶段与验收样本

### 阶段 A：模型与同步底座

落地来源身份、扫描清单、媒体身份、版本、产物和任务队列；替换全量数组和无差异 Upsert。验证固定连接变更门控、增量已完成但全量仍待对账、共享游标、热目录退避与索引缺失退化策略、全量一致性、低 ID 复用、源库替换、异常不误标缺失、崩溃续跑和重叠范围。浏览选择入库转为 SQLite 路径定位，删除 AList 追更调度和非浏览/搜索资源 API 依赖。

### 阶段 B：电影与节目识别

实现类型分流、目录级绑定、季集解析、季缓存与人工纠偏。验证纯数字平铺、标准 Season 目录、TMDB 标签目录、同名不同年份电影、特别篇和不能自动确定的综艺分段。

### 阶段 C：标准产物与发布

用固定元数据测试夹具生成“八仙！”电影目录和“折月亮”节目目录，检查 XML、命名、图片归属、原播放定位保留、重复执行幂等、改绑后旧任务不覆盖、生成中断恢复。

### 阶段 D：Web 双界面、Emby/SenPlayer 与性能

用请求记录断言：仅后台浏览/搜索调用 AList list/search；单文件导入、整目录导入、追更、附件下载、播放及失败重试不调用 AList 资源 API。覆盖“浏览可见但 SQLite 暂无节点”、SQLite 暂时不可用、签名过期和文件入口重定向循环，检查明确错误及零 API 兜底。

Web 验证默认进入展示页、管理员与普通用户入口差异、直接访问管理路由及 API 的拒绝行为、伪造本地权限和服务端角色撤销。用网络请求检查展示页仅从 Emby API 获取媒体数据，不请求管理台账、不调用 AList；管理员操作完成后通过 Emby API 刷新预览。桌面与手机验证电影详情和节目季集导航、加载/空数据/失败状态。

接口验证电影详情、节目季列表、按季选集、正确 DTO、播放版本和观看进度；SenPlayer 实机验证海报墙→详情→季→集→播放。独立 Emby 扫描样本目录作为标准输出的兼容检查。执行上述规模压测后调整低功耗默认值。

完成标准：不依赖额外重服务，电影和节目均可规范落地；无季纯数字节目可正确选集；无变化对账不会触发全库刮削；后台任务有可恢复状态和可测资源上限。
